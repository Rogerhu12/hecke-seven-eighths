## 规矩

1. **只改本组文件**，清单见 `.github/groups/gN.txt`。在别的组的文件里发现问题，在 PR #9 上告诉那个组，不要自己改。
2. **只改证明，不用报备**。错误在证明体里时直接修。按规矩 6，编译选项（例如 linter、heartbeat）也可以直接加。
3. **改陈述或定义要公告**：只有在非改不可时才改，例如定义编不过、陈述有缺陷、universe 没定、换行的 `.field` 被当成参数。规矩 3 仍然适用：最终结论不能削弱。改动步骤如下：
   - 在 PR #9 贴出新旧文本，说明原因；A2 有异议会提出来。
   - 然后更新骨架：在骨架分支上，把你改过的整份文件放进去，运行 `python3 .github/groups/skeleton.py make <文件>` 把证明换成 `sorry`，再提交推送。只能这样更新你自己组的文件。
   - 各组 PR 的 CI 跑在"骨架 + 本组"的合并结果上，所以骨架更新后，下一次运行会自动用上新版本。
4. **本组以外的失败**说明骨架里某个文件的定义或陈述有错。在 PR #9 上通知那个文件所在的组。在它修好之前，先修本组其余的错误。
5. **换行投影已经批量合并过**：`.github/groups/join_projections.py` 已经把所有"上一行以 `)` 结尾、下一行以 `.field` 开头"的写法合并成了一行，骨架和各组的真实文件都改过。少数地方的 `.x` 其实是传给上一行函数的参数，不是投影（例如 `CanonicalLiteralRectangles` 里的 `.left b.val.2.1 …`）。这种地方合并之后会报 `Invalid field`，把那一行拆回去就好。
6. **慢文件**：单个模块超过 20 分钟会被杀掉。先确认 linter 已经关了（骨架里已经统一关掉）；如果还慢，就改写证明，例如拆出中间引理，或者避免让 `simp`/`rfl` 展开巨大的项。
7. 每次提交都按规矩 4 带上 ChatGPT 的署名行。不要推送 `dtests-handoff`、`cloud/mom-engine-step` 或别的组的分支。

## 完成标准

- 本组 PR 的 CI 全绿：本组全部模块编译通过；本组文件里没有 `sorry`、`admit`、`native_decide`、`axiom`；没有模块被杀。
- 本组改过的每一处陈述或定义都已经在 PR #9 公告，并同步到骨架。
- 满足以上两条后，把 PR 标为 ready。协调员会把它合进骨架分支，骨架里本组的 `sorry` 就换成了真实证明。
